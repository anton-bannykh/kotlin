# Interop lowerings

*Skip this page if you already know how an interop call becomes a C stub plus an `external` bridge in the IR. Reference material.*

How a C call works end to end (the cinterop klib, the stubs, clang) is in [cinterop.md](../../interop/cinterop.md). This
page shows only what changes in the IR. Three lowerings form a chain that runs after inlining:

`InteropLowering → SpecialInteropIntrinsicsLowering → InteropBridgesNameInventor`

The other two are independent: a check for `autoreleasepool`, and a fix for [Swift export][swiftexport] bridges in the first
stage.

## InteropLowering

Replaces every use of a declaration from a cinterop library (a C function, a C global, an Objective-C method or constructor)
with a call to a generated **bridge**: a small C function (the **C stub**) plus an `external` Kotlin function bound to it.

**Why:** a function such as `add` in a cinterop klib has no body, only annotations saying which C symbol it stands for.
The real call is made by generated C code, so that a C compiler handles the C side.

```kotlin
// before        (mylib is a cinterop library made from:  int add(int, int);  int apply(int (*f)(int), int);)
fun callC(x: Int): Int = add(x, 2)
fun callback(x: Int): Int = apply(staticCFunction { v: Int -> v * 2 }, x)

// after
fun callC(x: Int): Int = interopCallMarker({    // marks "all bridges of one interop call"; removed by the name inventor
    @KotlinToCBridge(language = "C", library = "mylib", impl = """
        extern const int (*␀target2␀)(int, int) __asm("knifunptr_mylib_add_0");   // pointer to add, exported by the library
        int ␀knbridge1␀(int p1, int p2) { return ␀target2␀(p1, p2); }""")          // the C stub, as text
    @FilterExceptions(mode = "terminate")       // a foreign exception escaping from C terminates the program
    external fun ␀knbridge1␀(p0: Int, p1: Int): Int                              // Kotlin side: declared, bound to the stub
    ␀knbridge1␀(x, 2)
})
fun callback(x: Int): Int = interopCallMarker({
    external fun ␀knbridge1␀(p0: CPointer<CFunction<(Int) -> Int>>?, p1: Int): Int     // bridge to apply, as above
    ␀knbridge1␀({
        fun anonymous(v: Int): Int = v * 2                                        // the lambda, now a plain function
        @CToKotlinBridge fun ␀knbridge1␀(p0: Int): Int = anonymous(p0)            // Kotlin function that C may call
        @KotlinToCBridge(impl = "int ␀kncfun2␀(int p1) { return ␀knbridge1␀(p1); }")   // C function that calls it
        external fun ␀kncfun2␀(): Int
        ::␀kncfun2␀                             // staticCFunction is now the raw address of that C function
    }, x)
})
```

**Know this**
- The names are placeholders between NUL characters (`␀` above), numbered within one interop call only.
- Objective-C works the same way (not shown: it needs macOS). A method call gets a stub written in Objective-C that sends
  `@selector(...)` to the receiver. A Kotlin class that extends an Objective-C class also gets extra functions, for example for
  `@ObjCAction` methods, so that the [Objective-C runtime][objcrt] can call into it.

**Source:** [InteropLowering.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/lower/InteropLowering.kt),
[CBridgeGen.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/cgen/CBridgeGen.kt) (what a bridge looks like)
· **Runs:** after inlining, always.

## SpecialInteropIntrinsicsLowering

Replaces the cinterop intrinsic `typeOf<T>()` (the one in `kotlinx.cinterop`, not `kotlin.reflect.typeOf`) with the companion
object of `T`, which holds the size and alignment of the C type. `sizeOf<T>()`, `alignOf<T>()` and `alloc<T>()` are inline
functions built on it, and which class `T` is becomes known only after they are inlined into the caller.

```kotlin
// in kotlinx.cinterop
class IntVarOf<T : Int>(rawPtr: NativePtr) : CPrimitiveVar(rawPtr) { companion object : Type(4) }   // size 4, alignment 4
inline fun <reified T : CVariable> sizeOf(): Long = typeOf<T>().size

fun size(): Long = typeOf<IntVarOf<Int>>().size         // before (sizeOf is already inlined)
fun size(): Long = IntVarOf.Companion.size              // after
```

Every class that describes a C variable (`IntVar`, a struct generated by cinterop, …) must have such a companion: if it has
none, compilation fails here. A `typeOf<T>()` whose `T` is still a type parameter (in the leftover body of the inline
function itself) is left alone.

**Source:** [SpecialInteropIntrinsicsLowering.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/lower/SpecialInteropIntrinsicsLowering.kt)
· **Runs:** after inlining, always, right after `InteropLowering`.

## InteropBridgesNameInventor

Gives the bridges their final, unique names, in the Kotlin declarations and in the C text alike, and hands the C text over
to be compiled by clang.

**Why:** bridge names become symbols in the binary, so they must be unique across the whole program.

```kotlin
// after: `callC` from above. PFX is a long hex string, see below
fun callC(x: Int): Int = {                                  // the marker is gone
    @KotlinToCBridge(..., impl = "... int _PFX_1_knbridge1(int p1, int p2) { return _PFX_1_target2(p1, p2); }")
    @SymbolName("_PFX_1_knbridge1")                         // binds the Kotlin declaration to the C function
    external fun _PFX_1_knbridge1(p0: Int, p1: Int): Int
    _PFX_1_knbridge1(x, 2)
}
```

**Know this**
- A name is `_<prefix>_<n>_<placeholder>`. The prefix is the module name plus the file path, written as hex bytes, so it is
  unique per file. `n` counts the interop calls in the file. This is why bridge symbols look like `_36636437…_1_knbridge1`.
  A bridge in the other direction (C calls Kotlin) gets `@ExportForCppRuntime` with the new name instead of `@SymbolName`.
- It has a side effect outside the IR: every C stub is registered for compilation, and the cinterop library named in the
  bridge is recorded as a dependency of the file.

**Source:** [InteropBridgesNameInventor.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/lower/InteropBridgesNameInventor.kt),
[CStubsManager.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/CStubsManager.kt) (compiles the stubs)
· **Runs:** after inlining, always.

## SpecialObjCValidationLowering

Reports a compilation error when a `suspend` function is called inside `autoreleasepool { }`. It changes nothing in the IR.
[Autorelease pools][autorelease] form a stack. If the block suspends, the coroutine's caller goes on while the pool is still
open; when the caller closes its own pool, the inner one is closed with it, and resuming the coroutine later crashes.

```kotlin
inline fun <T> myPool(block: () -> T) = autoreleasepool(block)
fun later(f: suspend () -> Unit) { ... }

suspend fun load() {
    autoreleasepool { fetch() }             // error: calling suspend functions from `autoreleasepool {}` is prohibited
    myPool { fetch() }                      // the same error, although `autoreleasepool` is not called here directly
    autoreleasepool { later { fetch() } }   // allowed: the call is in a local function, not in the block itself
}
```

The check is not in the frontend because of the indirect case (`myPool`). After inlining it is easy: the block's code sits
inside the marker that the inliner leaves around the pasted body of `autoreleasepool` (see [inlining.md](inlining.md)).

**Source:** [SpecialObjCValidationLowering.kt](../../../../kotlin-native/backend.native/compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/lower/SpecialObjCValidationLowering.kt)
· **Runs:** right after `NativeAllFunctionInlining`, always.

## NativeExportedBridgeCallDispatchLowering

Inside a Swift export bridge marked `@ExportedBridge(..., nonVirtualTargetMethod = "name")`, turns the call of the method
`name` from a virtual call into a direct call of that exact implementation, as `super.name()` would be.

**Why:** Swift export lets a Swift class inherit from a Kotlin class (see [export.md](../../interop/export.md)), and then the
virtual-table entries of the Kotlin object point to the Swift methods. When Swift needs the inherited Kotlin implementation
(a `super` call, or a method it did not override), a virtual call would land in Swift again and recurse forever.

```kotlin
open class Base { open fun greet(name: String) = "hi $name" }

// before: two bridges with the same body
@ExportedBridge("Base_greet")
fun Base_greet(self: Base, name: String): String = self.greet(name)                 // stays a virtual call
@ExportedBridge("Base_greet_direct", nonVirtualTargetMethod = "greet")
fun Base_greet_direct(self: Base, name: String): String = self.greet(name)

// after
fun Base_greet_direct(self: Base, name: String): String = self.super<Base>.greet(name)   // always Base.greet
```

**Know this**
- A non-virtual call on another object cannot be written in Kotlin source, so the bridge generator emits a normal call
  plus the annotation argument. A call of an abstract method is left virtual.
- The same annotation marks the bridge that runs the constructor of an abstract or sealed Kotlin class for a Swift subclass.
  There the constructor call becomes a delegating constructor call (the IR form of `super(...)`); a plain constructor call
  of an abstract class would be replaced by a linkage error when the klib is loaded.

**Source:** [NativeExportedBridgeCallDispatchLowering.kt](../../../../compiler/ir/backend.native/src/org/jetbrains/kotlin/backend/konan/lower/NativeExportedBridgeCallDispatchLowering.kt)
· **Runs:** in the first stage, always, before the IR is written to the klib.
